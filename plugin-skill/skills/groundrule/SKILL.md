# Groundrule

The repository's engineering standards live in `.groundrule/` and reach you through the agent file (`AGENTS.md` or `CLAUDE.md`), which `groundrule sync` writes. The standards are the team's decisions, not suggestions: a blocking rule fails the pull request in CI, so code that breaks one will not merge. Everything below runs the open-source CLI with `npx @groundrule/cli`; it works offline and without an account.

## Before editing

Read the rules in the agent file. Rules under a path heading apply to files under that path; rules under "Everywhere" always apply. For the whole list with each rule's severity, run `npx @groundrule/cli standards`. For one rule in full (why it exists, examples, how to comply, the exceptions that apply), run `npx @groundrule/cli explain <ID>`.

## Before running a command or a tool

The agent file may have a section "What you may not do alone": the team's action policies. _never_ means do it another way or ask the developer; _ask first_ means the developer confirms before you run it. Follow them even when nothing stops you. If a hook refuses a call or asks for confirmation, its reason names the policy and what to do instead: do that. Never retry a refused action in another form, and never edit the policies or `.groundrule/exceptions.yaml` to get past one.

## Before finishing

Run `npx @groundrule/cli check`. It runs the same check CI will run, on the uncommitted changes only, and lists what the change introduced: the rule, the file and line, and the fix. Fix every blocking finding before you stop, then run it again. Warnings are worth fixing when the change is small; say so when you leave one.

## Make it automatic

This plugin is the skill only. Two things make the rules arrive without you asking, and both are set up in the repository itself so every developer's agent gets them. Offer them once, and run them only when the user agrees:

- `npx @groundrule/cli hooks` adds two hooks to `.claude/settings.json`: one decides each shell command, edit, read and tool call against the action policies before it runs, and one runs the check when you finish and sends you back if a blocker remains. The user commits the file.
- `claude mcp add groundrule --scope project -- npx -y @groundrule/cli mcp` adds an MCP server with `rules_for` (the rules for a file), `check`, `list_standards` and `propose_rule`.

## When the user corrects you

If the user says a correction should apply to everyone ("we never do X here", "always use Y"), offer to propose it: `npx @groundrule/cli propose "<the rule in one sentence>" --why "<reason>" --file <path>:<line>`. It needs a repository connected to a Groundrule workspace, and nothing changes until a reviewer there accepts it. Only run it when the user agrees.

## What never to do

Do not weaken or delete a standard, add an exception, or edit the generated agent files to make a check pass. Exceptions are written by the team in `.groundrule/exceptions.yaml` with a reason, an approver and an expiry. If a rule is wrong for this code, say so and propose the change; do not route around it.

## When there is no `.groundrule` folder

There are no standards to follow yet. If the user wants them, `/groundrule:setup` sets the repository up: it detects the stack, picks packs, writes the agent files and runs the first check.
