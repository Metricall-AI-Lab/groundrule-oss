# Groundrule

The repository's engineering standards live in `.groundrule/` and are served by the `groundrule` MCP server. The standards are the team's decisions, not suggestions: a blocking rule fails the pull request in CI, so code that breaks one will not merge.

## Before editing a file

Call `rules_for` with the file's path. It returns the rules that apply to that file, blocking ones first, each with how to comply. Rules that apply everywhere are already in the agent file, so this is only the file-specific set. The plugin's PreToolUse hook does this automatically once per file per session; call it yourself when you plan a change across several files.

## Before running a command or a tool

The repository may have action policies: what you may run on your own, what the developer confirms first, and what is refused. They are listed in the agent file under "What you may not do alone", and the plugin's PreToolUse hook decides each shell command, edit, read, fetch and MCP call against them before it runs. When a call is refused or needs confirmation, the reason names the policy and what to do instead: do that, or ask the developer. Never retry a refused action in another form, and never edit the policies or `.groundrule/exceptions.yaml` to get past one.

## Before finishing

Call `check` with no arguments. It runs the same check CI will run, on the uncommitted changes only, and lists what the change introduced: the rule, the file and line, and the fix. Fix every blocking finding before you stop. Warnings are worth fixing when the change is small; say so when you leave one. The plugin's Stop hook runs the same check and will send you back if a blocker remains.

## When the user corrects you

If the user says a correction should apply to everyone ("we never do X here", "always use Y"), offer to propose it with `propose_rule`: the rule in one sentence, why, and the file and line where it came up. Nothing changes until a reviewer in their workspace accepts it. Only call it when the user agrees.

## Explaining a finding

`list_standards` returns every rule in effect. For one rule, the CLI gives the full story: `npx @groundrule/cli explain <ID>` prints the requirement, why it exists, examples, how to comply, and the exceptions that apply.

## What never to do

Do not weaken or delete a standard, add an exception, or edit the generated agent files to make a check pass. Exceptions are written by the team in `.groundrule/exceptions.yaml` with a reason, an approver and an expiry. If a rule is wrong for this code, say so and propose the change; do not route around it.

## When there is no `.groundrule` folder

The hooks and tools do nothing. If the user wants standards, `npx @groundrule/cli init` detects the stack and picks packs, `sync` writes the agent files, and `check` runs the rules. Everything works offline and without an account.
